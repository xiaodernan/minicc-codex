# 需求与开发计划：小游戏完善与 minicc 产品差距

## 1. 目标与验收标准

本轮目标分为两个部分：完成内嵌“植物大战僵尸”战役体验；明确 minicc 相对成熟 coding agent 产品的工程缺口和实施优先级。

### 1.1 已实现的小游戏需求

| 需求 | 实现 | 验收标准 |
| --- | --- | --- |
| 消除战役超时失败 | 删除循环中基于 `GAME_DURATION` / `game.timeUp` 的结束分支；只在僵尸到达房屋时失败 | 持续游玩超过旧时限不会结束；仅 `zombie.x < 61` 可触发失败 |
| 正确计时与后台保护 | 仅在活动帧累计 `elapsed`；标签页隐藏和手动暂停会停止 RAF、音乐和计时，恢复时重置 `last` | 后台等待、手动暂停不增加“战斗用时”，恢复后无大步长跳帧 |
| 高难度模式 | 标准、高压、噩梦三档；影响初始阳光、每波数量、僵尸血量、速度、类型概率及刷怪间隔 | 选择难度后新战役的上述参数均发生确定性变化；战斗中不可切换避免状态失真 |
| 战斗信息 | 波次威胁进度、强化波提示、实时击退数、阳光、战斗用时 | HUD 与当前 `waveSpawned/waveTarget` 同步 |
| 战斗控制 | 手动暂停/继续、铲子、自动拾取阳光、音量、音效开关 | 暂停原因区分手动与页面隐藏；页面恢复不会错误取消手动暂停 |
| 音效体验 | Web Audio 合成收集、种植、射击、命中、爆炸、波次、胜负及近屋危险预警；带节流和总音量持久化 | 无 AudioContext 时游戏仍可运行；高频命中不会造成失控的音频节点增长 |

### 1.2 本轮非目标

- 不引入外部图片、音频版权资源或联网依赖。
- 不把小游戏接入服务端存档、账号、排行榜或付费系统。
- 不宣称已完成跨浏览器视觉回归；当前仓库没有 Playwright/E2E 基础设施。

## 2. 已落地设计

### 2.1 战役状态机

`web/app.js` 中战役结束仅保留两类状态：

```text
全部 10 波生成并清除 -> victory
任一僵尸穿过房屋防线 -> gameOver
```

`elapsed` 是展示指标而非失败条件。每帧使用上限为 80ms 的 `dt`，暂停恢复时将 `last` 重置为 `performance.now()`，避免浏览器切换标签页后将空闲时间结算进战局。

暂停使用 `pauseReasons: Set` 保存来源：

```text
manual + visibility -> paused
visibility 解除但 manual 保留 -> 仍暂停
所有原因解除 -> 恢复 RAF、音乐和活动帧计时
```

### 2.2 难度参数

| 档位 | 初始阳光 | 血量 | 移速 | 生成间隔 | 每波修正 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 标准 | 200 | 0.90x | 0.90x | 1.16x | -1 |
| 高压（默认） | 175 | 1.00x | 1.00x | 1.00x | 0 |
| 噩梦 | 150 | 1.28x | 1.16x | 0.80x | +2 |

这些倍率集中在 `GAME_DIFFICULTIES`，可用于后续平衡迭代；不能仅修改标题或波次数量来伪造难度。

### 2.3 后续小游戏迭代

| 优先级 | 需求 | 交付物 | 验收方式 |
| --- | --- | --- | --- |
| P1 | 冷却和种植反馈 | 卡片 cooldown、放置预览、不可放置原因 | E2E 检查不能重复种植、冷却状态与点击反馈 |
| P1 | 敌人行为扩展 | 特殊僵尸、行进/攻击动画、按行预警 | 固定随机种子下的波次仿真 |
| P1 | 存档与继续 | `localStorage` 战役快照、版本化 schema | 刷新页面后恢复且 schema 升级不崩溃 |
| P2 | 可访问性 | 键盘格子导航、暂停焦点管理、音频可独立关闭 | axe + 键盘 E2E |
| P2 | 自动化体验验证 | Playwright 桌面/移动截图、Canvas 非空像素、暂停与胜负用例 | CI 中运行 Chromium 测试 |

## 3. minicc 现状证据

当前项目已有：OpenAI 兼容工具调用、只读/写入权限边界、路径约束和原子编辑、SQLite 任务记录、SSE、Docker 可选沙箱、MCP stdio、Git worktree、StateGraph/DAG、受白名单约束的验证器、completion judge，以及确定性复杂度驱动的只读子任务编排。详细边界见 `README.md` 和 `docs/AGENT_LLM_ROADMAP.md`。

这不是完整 Claude Code 或 Codex 产品的复刻。以下计划按“先提升可靠性和可评估性，再扩大自动化能力”排序。

比较基准仅使用项目现状及公开官方 Codex 仓库，未将第三方教程作为能力证据。官方 Codex CLI 仓库：<https://github.com/openai/codex>。

## 5. 建议实施顺序

1. **P0 可靠性基线（本轮已落地本地版本）**：任务评测 fixture、Playwright、重启 checkpoint、权限审计均有实现和测试；真实模型质量/成本/延迟看板仍待接入原始运行数据。
2. **P1 执行质量（本轮已落地受约束初版）**：动态 DAG、依赖感知 repair、上下文索引和模型路由已接入；真实对比评测和更完整的失败分支仍是后续工作。
3. **P2 产品扩展（按需求）**：MCP 扩展、IDE 协作、Git 工作流。以安全模型和可观测数据成熟为前提。

## 6. 风险与决策

- 不把“多 Agent”作为优先功能。没有评测、隔离、证据归并和失败恢复的并发只会放大成本与不可控性。
- 不把模型自然语言结论视为完成依据。写入后必须保留 diff、命令、退出码和验证证据。
- 不在 host 执行模式下默认信任陌生仓库。需要 Docker 可用性检查、明确授权和可审计记录。
- 小游戏当前使用 Web Audio 合成音，优点是无资源部署成本；若改用采样音频，需补版权来源、预加载、失败降级和音量混音策略。
