# minicc-codex 整体评审

评审日期：2026-09-18。范围为当前工作区（包含已有未提交改动）。本次没有修改业务代码，也没有调用真实模型产生费用。

整体判断：单机本地 coding agent 的产品方向和技术选型合理，工具、流式输出、验证、恢复、任务管理都已经有实现。下一阶段优先收紧这些机制之间的契约、修复真实仓库下的检索和性能问题，再扩展功能。现有评测不足以给出可信的“编码准确率”。

## 本次验证与证据边界

- 浏览器实际查看 1440×1000 桌面亮/暗主题及 390×844 手机布局；控制台未见错误。
- 使用临时 MINICC_HOME 启动独立本地服务；模型端点禁用，没有提交模型任务。
- `npm run check:web` 通过，说明当前构建产物与模块源码一致。
- 27 项定向测试通过：检索、权限及上下文压缩、验证器、完成判定解析的相关测试。没有跑全量回归。
- 用最小输入复现检索漏源文件、压缩工具消息失配、完成判断字段缺失等问题；后端评审还对权限传递、恢复心跳、流窗口进行定向复现。
- 本地耗时是当前 Windows 工作区观测值，不等同于生产 p95 或模型端到端性能。已有 output/evaluation-full.md 是历史报告，本次没有重跑其中的模型评测。

## 一、准确率与完成质量

### 1. 优先修复检索入口

位置：`minicc/agent/retrieval.py:396`，`minicc/web.py:694`。

当前 `_files()` 使用 `rglob('*')` 递归所有目录，先累计扫描文件数，再过滤 `.git`、`.minicc`、依赖和输出目录。在本工作区，4000 文件额度大部分被隐藏目录占用。独立实测只索引 31 个文件、2 个符号，`minicc/` 源文件数为 0；搜索 `run_agent` 返回 README、配置文件和历史 Playwright 快照。其他工具仍能直接读源码，但这个前置定位机制没有发挥应有作用。

建议先使用可剪枝目录遍历或 Git 文件清单，保留合法未跟踪源码，遍历前排除依赖、缓存及 `.playwright-cli`；按路径、mtime/digest 缓存并增量更新。当前每次聊天重新建索引，本次单次约 0.89 秒。检索排序应先确保存在查询相关性，再加入新鲜度；后续用真实定位任务测 recall@k 和首个正确位置排名。

### 2. 重新定义评测口径

位置：`benchmarks/tasks.json:27`，`minicc/benchmarks.py:62`、`:215`、`:252`，历史 `output/evaluation-full.md:7`。

历史报告的 `pass_at_1=1.0` 只覆盖 3 个可评分任务，其余 27 个是 N/A。3 个 grader 中两个是 `pytest --collect-only`，另一个是 JS 语法检查，不能证明回答或修复正确。执行器对全部任务设置 `allow_changes=False`，所以 edit 类 fixture 也没有验证实际编码。失败任务仍可能因 grader 退出码为 0 被计为 passed。

建议分别报告：运行完成率、可评分覆盖率、验收成功率、错误宣称完成率、p50/p95 延迟及每次成功任务的 token 成本。先建设 10–20 条高质量任务：隔离临时仓库、预置缺陷、隐藏行为测试、只读问题答案 rubric；记录模型、参数、代码提交及 fixture 版本，固定样本比较改动前后。不得把内部组件测试通过率当作 Agent 准确率。

### 3. 上下文压缩按完整工具轮次切分

位置：`minicc/agent/context.py:309`、`:176`、`:237`。

目前按最后 6 条消息硬切。最小复现压缩后仍有 `tool_call_id=read1` 的工具结果，但对应 assistant tool call 已被移除。原生工具协议可能因此拒绝请求。目标提取仅保留最早 3 条用户目标，也会使多轮修正失去优先级。

建议把 assistant tool calls 和所有对应结果作为不可拆分组，发送模型前校验配对；另存原始目标、最新有效约束、已完成步骤、待办与最近失败，后续用户修正按实体覆盖旧约束，而不是旧字符串永久占满容量。

### 4. 验证应匹配改动和用户目标

位置：`minicc/agent/verifier.py:91`、`:113`，`minicc/web.py:1528`。

存在 tests 目录就默认 `python -m pytest -q`，传入多条验证命令也只运行第一条。这样前端小改动会触发全量 Python 测试，却没有检查对应 UI 行为。

建议引入 VerificationPlan：由变更路径、任务类型和工程配置选择定向测试、类型检查、构建或浏览器关键路径检查。已通过验证与文件 digest 绑定，没有相关新变化时复用。只有依赖升级、跨模块重大改动或发布集成关口再扩大到全量回归。

### 5. 完成评估需要结构化客观门槛

位置：`minicc/agent/completion.py:209`、`:339`，`minicc/web.py:1622`。

最小输入 `{"status":"complete"}` 会被接受，尽管 confidence 为 0，rationale/evidence 为空。证据包先 JSON 序列化再截最后 28000 字符，长证据下会成为无效 JSON，并丢失前面的事实。

建议先按事件重要性裁剪，再序列化完整结构；要求判定绑定需求验收项、实际 diff/工具证据与相关验证。complete 必须满足确定性前提；模型的 confidence 只能作为辅助指标，不能代替验收。

## 二、前端美观和交互

亮色桌面的三栏布局、任务侧栏、输入卡片和本地化图标已经有产品形态。主要问题是视觉系统经过多次覆盖，亮暗主题表现不一致，核心任务动作不够清晰。

### 可复现的可用性问题

- **手机发送按钮被裁切**：390×844 下，38px 菜单栏之外 `.main-column` 仍为 844px，内容底部到 882px；发送按钮下沿为 856px，超出可视区 12px。位置 `web/styles.css:898`。应让主体占父容器剩余高度，并验证 `100dvh`、安全区和软键盘状态。
- **暗色主题部分文字几乎不可读**：文件名仍使用 `rgb(63,65,66)` 等深色，背景已变暗；顶栏仍为浅蓝。主题切换还改变了部分字号和导航显示。应统一语义色变量和组件结构，让主题主要改变颜色；正文/常规标签对比度目标至少 4.5:1。
- **权限文案和入口不一致**：同时出现“默认/计划/自动写/全自动”“安全模式”，提示又引用“完全访问”；联网开关被 `.safe-toggle:nth-child(2) { display:none; }` 隐藏（`web/styles.css:1413`）。应提供一个清晰权限入口，直接显示文件修改、命令执行、联网三项当前能力。
- **工具按钮只剩图标**：CSS 隐藏文字后，部分按钮在无障碍树里没有可用名称。补齐 aria-label、tooltip、键盘焦点，并保证触控区域。

### 视觉改进建议

1. 常规正文 14–16px，辅助信息尽量 12px 以上；减少当前 9–11px 文件元信息和指标。
2. 新任务空态提供 3 个具体起步动作与当前工作区摘要，收起没有内容的指标；会话中把回答、变更、验证作为主层级。
3. 右栏可切换“变更 / 文件 / 验证”，文件只保留一个主列表；概要指标逐步展开，避免重复占位。
4. 将宣传页、小游戏等辅助入口移至次级位置；小游戏脚本按需加载。
5. 整理统一 spacing、字体、颜色、圆角与按钮状态。`styles.css` 目前 2386 行，包含多轮参考样式与后续覆盖，继续尾部补丁会增加主题回归风险。

## 三、性能与速度

### 1. 首屏最明显的等待来自改动摘要

位置：`minicc/changes.py:120`、`:153`、`:182`，`web/src/chat/stream.js:343`，`web/src/main.js:390`。

一次浏览器初始加载资源约 0.7 秒，但 `/api/changes` 约 9.27 秒。独立插桩发现摘要处理 107 个文件，启动 1 次 git status 和 77 次 git show；仅 git show 合计 8.41 秒。启动逻辑等它完成才结束 splash；另一次刷新实测 DOM ready 146ms，工作台 ready 10951ms。

建议列表用批量 `git diff --numstat` 配合 `git status --porcelain -z`，完整 patch 点击时再算；新增文件单独统计。工作区状态、历史、文件树和改动区独立加载，启动页只等必要元数据；增量缓存加失效机制。验收目标可先设为同工作区摘要低于 1 秒、工作台主体不被它阻塞，修复后实测确认。

### 2. 流事件不要每次同步写完整快照

位置：`minicc/task_worker.py:156`，`minicc/task_store.py:49`，`minicc/task_manager.py:2146`。

进程 worker 每个 delta 都做脱敏、JSON 序列化、连接和写库；线程模式虽节流，持久化还会重复计算文件 digest。建议生成链路只发布小事件，持久化后台批量合并；终态与重要状态转换强制落盘，文件摘要只在相应变更后更新。SQLite 使用清晰的连接生命周期，按读写负载考虑 WAL。进程镜像固定 1.5 秒轮询也值得改为 IPC/事件通知。

### 3. 包体和前端渲染属于下一层优化

首页当前直接加载 app.js 约 269KB、game.js 约 109KB、CSS 约 176KB，另有 Markdown 和高亮依赖。构建生成的约 181KB app.min.js 没有被页面引用；静态资源统一 no-store。

建议生产入口使用压缩且带内容 hash 的资源，HTML 保持更新检查，版本化资产使用长期缓存；游戏和不常用面板按需加载。已有 120ms 流渲染节流和历史长度限制值得保留。再针对长会话测量：事件变动现在会重建整段 timeline，滚动定位遍历全部消息；必要时改增量节点更新及虚拟列表。这里尚未做长会话压测，不能直接宣称已存在严重卡顿。

## 四、后端及前后端架构

继续使用单体本地服务、SQLite、本地 worker 与 SSE 是合理的；当前收益更高的是统一协议和职责边界。

### 1. 线程执行器权限字段丢失

`minicc/task_manager.py:1928` 构造 `_run_chat` payload 时漏掉 permission_mode；进程执行器却有传递。会导致 acceptEdits 变回 default；API 提交 plan + allow_changes=true 时，计划模式的保护也可能失效。普通前端会在 plan 下强制 allowChanges=false，因此不能把这一问题描述成所有 UI 计划任务都会写文件。

建议线程和进程共用类型化 TaskRequest，服务端统一解释权限，前端只负责展示。验证必须覆盖提交→调度→执行，而不只是快照是否保存字段。

### 2. 重启恢复先检查存活，再改变状态

`minicc/task_manager.py:973` 在读取 running 任务后先改 interrupted 并持久化，快照未保留心跳；`:997` 随后才检查心跳。这样开启 auto-resume 后可能重排仍活着的 worker。心跳又依赖模型输出回调，长时间无输出不代表进程死亡。

建议 worker PID、lease owner、heartbeat 独立保存，定时心跳与输出解耦；先确认/重连，再通过原子状态更新认领或重跑。验收用真实子进程验证重启期间同一任务只执行一次。

### 3. 流游标必须单调增长

`minicc/task_worker.py:157` 保存 16000 字符尾窗口，而 `minicc/task_manager.py:1783` 用窗口长度增长计算增量，满窗口后后续文字不再实时更新，最终完整结果可能仍能返回。

建议协议使用 sequence 和绝对字符/字节偏移，窗口长度仅用于展示；测试超长回答、截断、断线重连、重复和丢失事件。

### 4. 按责任拆模块，同时保持单一契约

- 后端：HTTP/RPC adapter → TaskService → AgentRuntime → Executor / Repository。web.py 1830 行、task_manager.py 2236 行、loop.py 1392 行，拆出调度、恢复、验收、附件和持久化。
- 前端：transport → store/reducer → view。api、stream、markdown、panels 目前相互循环 import，文件拆开了但责任仍纠缠；panels/index.js 1632 行。先理清依赖，再按需要逐步增加 TypeScript，框架迁移本身不会修复这些问题。
- 统一 TaskRequest、TaskResult、TaskEvent 的字段与 schema_version，线程/进程/SSE/历史恢复共用定义。针对接口边界补少量有价值的契约测试。
- 清理确认无引用的旧 01–09 分片与临时迁移脚本，避免维护者修改未参与构建的文件；文档同步当前模块入口。
- 历史量较大时再考虑 SQLite FTS5、workspace 索引和分页，无需当前就增加外部服务。

## 建议实施顺序

1. **执行正确性**：统一 TaskRequest、修检索遍历、工具轮次压缩、恢复租约；每项用一个直接复现问题的定向用例验收。
2. **建立可信质量闭环**：分离评测指标，建设小型行为验收集，按改动选择验证，完善完成评估结构。
3. **快速改善体感**：批量 Git 摘要、启动并行、手机高度、暗色对比度、权限入口一致性。
4. **持续维护与规模化**：事件持久化与长流协议、前后端模块边界、样式整理、按需加载，再基于实测决定进一步并发优化。

这四步应分别比较结果正确率、误报完成率、首次可用时间、首次有效输出时间、总耗时和恢复成功率；避免用新增机制数量或测试数量代替实际改善。
