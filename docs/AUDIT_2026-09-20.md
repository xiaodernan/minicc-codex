## 二、总体评价

**引擎已经接近 Claude Code / Codex 的同级设计，产品外壳与可信度还差两级。**

做得真实且好的部分（不是摆设）：

- **按完整工具轮次压缩上下文**（`context.py` 的 `_recent_boundary` 反向走保留尾段，保证每个保留的 tool result 都带着它的 assistant call），`repair_interrupted_tool_rounds` 用显式 `[INTERRUPTED_TOOL_RESULT]` 标记收尾而不是伪造成功——这是很多 agent 做错的地方。
- **证据驱动完成判定**（`completion.py` 的 `_enforce_completion_evidence`）会交叉核对最近一次非 skipped 的验证结果、逐命令通过历史（后发生的失败不会被先前的通过抹掉）、要求被引用的事件编号真实存在于 judge 看到的证据包里。
- **双协议 Provider 的重试边界**比同规模项目严谨：永久性 4xx 不重投、Retry-After 封顶、已交付文本不重投（`ResponsesPartialError` / `AnthropicPartialError`）。
- **子代理隔离是结构性的**：`ToolRegistry.restrict(SUBAGENT_TOOLS)` 物理排除 `task` 工具，递归在构造上不可能。
- **资源边界纪律**：`MAX_TOOL_CACHE_ENTRIES` LRU、trace/usage/compaction 修剪、网络熔断、Verifier 16 项通过缓存。
- **测试质量**：AST 扫查 388 个测试函数，无恒真断言、无 mock-only 测试；有真实子进程测试（worker 存活、pytest 取消 <8s、故意放慢 `store.upsert` 钉住非阻塞契约）。

**但有三类地基随时失效，且都在最关键的位置：**

1. **会挂死**——`loop.py` 的恢复保护在纯文本回复时计数器永不自增，而 README 明说任务无总轮次上限。
2. **会静默损坏数据**——`openai_provider.py` 把只该用于"重试 attempt 全文对齐"的重叠合并，应用到每一个增量 delta 上。
3. **会泄密与自我提权**——agent 写一个 `.minicc/allowlist.json` 就能拿到全部 bash 权限；`workspace_roots` 只在四个入口中的一个生效。

**同时最刺眼的空洞是"不可证伪"**：`pass@1` 分母只有 3，CI 唯一端到端 web smoke 在 provider 指向不可达地址时仍打印 passed，`cost_per_success_usd` 恒 None。

## 三、P0：会挂死 / 会静默损坏数据 / 核心链路不可测

### P0-1 ✅ 流式增量重叠合并静默吞字符，污染 write_file / bash 参数

`minicc/llm/openai_provider.py:878`、`:884`、`:896`、`:898`；`minicc/agent/loop.py:191`、`:459`

```python
# openai_provider.py:877-880（_create_stream 内，每个增量 delta 都走这里）
attempt_text, _ = _merge_stream_text(attempt_text, str(content))
committed_text, suffix = _merge_stream_text(committed_text, attempt_text)
# :898 同一函数也用于 tool_call arguments 分片
slot["arguments"], _ = _merge_stream_text(slot["arguments"], str(function.arguments))
```

`_merge_stream_text`（`:240-254`）的 docstring 写的是"Merge a **retried full response**"，它的重叠去重分支是为"重试 attempt 回放累积快照"设计的：

```python
max_overlap = min(len(previous), len(current))
for size in range(max_overlap, 0, -1):
    if previous[-size:] == current[:size]:      # 尾部 == 头部 → 删掉重叠部分
        return previous + current[size:], current[size:]
```

**但它被应用到了每一个增量 delta 上。** 用项目自身函数实测（`.venv/Scripts/python.exe`）：

```
'hel' + 'lo'                      -> 'helo'          期望 'hello'        丢 1 字符
'aa' + 'ab'                       -> 'aab'           期望 'aaab'         丢 1 字符
'{"content":"aa' + 'aa"}'         -> '{"content":"aa"}'  期望 ..."aaaa"}  丢 2 字符
'line one\n' + '\nline two\n'     -> 空行被吃掉
```

工具参数分片实测：`["{\"path\":\"a", "a.txt\",\"cont", "ent\":\"hel", "lo world\"}"]` 组装出
`{"path":"a.txt","content":"helo world"}`——**`write_file` 静默写出内容错误但完全合法的 JSON**。

影响面：用户可见流式答案、最终 `answer`、`tool_calls[].function.arguments`（→ 写错文件内容、跑错命令）、`function.name`。

**为什么 388 个全绿测试没发现**：唯一相关测试 `tests/test_core.py:1510`
`assert _merge_stream_text("aa", "aab") == ("aab", "b")` 只覆盖了 `current.startswith(previous)` 的累积快照分支；`:1505-1508` 的 `deltas == ["aa","b","c"]` 同样是累积快照。增量 delta 分支零覆盖。

修复方向：同一次 attempt 内逐字节拼接；重叠去重只保留给重试 attempt 的完整文本对 `committed_text` 的合并（且仅对已知会重放累积快照的网关开启）。`loop.py:191` 是同一缺陷的第二份逐字拷贝，应抽 `minicc/llm/stream_merge.py` 统一后删除。

### P0-2 ✅ 恢复诊断阶段无限循环（纯文本分支计数器不自增）

`minicc/agent/loop.py:1263-1280`（纯文本分支）；计数器定义 `:51`、自增点 `:1210`（仅工具调用分支）

```python
if recovery_inspection_required:
    if stagnation_replans < STAGNATION_REPLAN_LIMIT:   # :1264 只读
        messages.append(assistant_msg(content=text or None))
        messages.append({"role": "user", "content": "[执行器恢复保护] ..."})
        continue                                          # 计数器不自增
    result.error = "Agent 在错误路径恢复阶段没有取得新的工作区证据"
```

`grep -n stagnation_replans loop.py` 只有 `:403`（初始化）、`:1209/:1210`（工具调用分支内自增）、`:1215/:1221/:1237`、`:1264/:1278`。**一旦进入纯文本分支（`:1263-1280`），该分支在 `continue` 前不自增任何计数器，`stagnation_replans` 停在进入时的值不再变化。**（注：计数器本身并非恒为 0——工具调用分支 `:1210` 会正常自增；缺陷是纯文本分支没有自己的退出计数。）

而 `loop.py` 的 docstring 与 README 都明确"Web/CLI 运行时没有任务级时长、轮次、token 或工具数量上限"——`web.py:730-733` 实际传 `Budget(max_turns=None, max_tool_calls=None, max_duration_seconds=None)`，`state.py:58-60` 的 `check()` 对 `None` 直接跳过，所以常规路径下没有后备上限，这是真正的死循环。

可达性：`web.py:1450` 传 `require_recovery_inspection=(agent_recoveries > 0 or repair_attempts > 0)`，即**每次 repair、每次 agent 恢复后都可能触发**。这是唯一一个"发起任务后必须人工杀进程"的缺陷。

修复方向：该分支加独立计数器（如 `recovery_refusals`）并在 `continue` 前自增。

### P1-7 ✅ SSRF 防护是 check-then-connect，无 IP 钉扎

且唯一的重定向测试 `tests/test_webfetch.py:111 test_redirect_followed` 开了 `monkeypatch.setenv("MINICC_ALLOW_PRIVATE_FETCH", "1")`，使 `netguard` 立即返回——**等于关掉守卫测重定向**。README:11 承诺的"重定向逐跳校验"无测试保护。

### P1-14 ✅ CORS 把任意 `*.local` 主机名当回环

## 七、安全模型评估

**设计是对的，执行有洞。**

`Editor._resolve`（reject 绝对路径 + `resolve()` + `is_relative_to(workspace)`）是真正扎实的 containment 原语——实测挡下 `..` 穿越、Windows 盘符、UNC、`\\?\` 前缀与 junction。STALE_CONTEXT 一致落地并审计，原子写用每次随机的临时名，输出脱敏分层（summary/head/tail/output/`data` 全过），子代理隔离是结构性的，webfetch 逐跳重校验（实现层面正确，缺测试与 IP 钉扎）。

**但权限模型信任了一个 agent 能写的文件**（`.minicc/allowlist.json`），白名单只在四个入口中的一个生效，网络门是子串黑名单，"只读验证命令"能跑任意 Python，回环绑定下没有 Origin 校验，0600 权限只在 POSIX 生效（Windows 上 web token 与 worker config 拿默认 ACL）。

**结论：作为单用户本地工具，默认配置下的实际风险高于 README 的描述。** 修 P1-1/P1-2/P1-3/P1-6 四项都是几行到几十行的改动，是整条路线图线性价比最高的一段。
